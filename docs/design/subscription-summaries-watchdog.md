# Subscription summaries and failure watchdog

Driven workers first write their own validated progress brief. Recovery asks the existing worker for a checkpoint, then uses `Drivers::recovery_summary(prompt)` for a fresh smaller worker. PID31 owns recovery classification and continuation; PID32 owns that shared summary seam and external seat folds.

`UNVRS_SUMMARY_ROUTES` is an ordered comma-separated list of exact `harness=model` pairs. Defaults: `codex=gpt-5.6-luna,claude=claude-sonnet-5-5`. Only Codex and Claude Code ship initially. Each route runs in an isolated working directory with restricted tools and no inherited API/PAT/workload-identity credentials. Codex checks the exact ChatGPT login-status response nonmutatingly, then uses exec with the same file auth store, ignored user config/rules and a read-only sandbox. This confirms auth mode and route readiness, not a paid plan or an effective-model echo; exec requests the exact model with `-m` and rejects tool, error and reroute items. Claude checks its subscription login and requests the exact model. Native delegation is disabled per invocation. No unpinned model fallback. Startup runs a real small request through every configured route; failures retain their reasons and immediately wake PID1. A failed route is skipped until restart, avoiding repeated quota requests. Every route attempt is journaled even if the next route succeeds.

The kernel tracks named jobs and drivers. Three consecutive failures wake PID1. An outstanding expected completion past its deadline also wakes PID1, checked every 500 ms by the socket loop, independently of the periodic worker threads. Completion resets the failure streak only on success. Alarms are deduplicated until recovery. Journal entries retain underlying reasons after credential redaction. The mechanism does not classify worker stops or restart workers.

Coverage: external folds and startup checks, driven worker and detached seat turns, quota refresh and memory sweep. Driver turn silence uses an explicit completion deadline, not an assumption that thinking emits progress. Route startup and summary turns have shorter deadlines. Persistence and journal write failures must also reach stderr; a broken journal cannot record its own outage.

Validation uses fake harnesses and fake time for deterministic checks, plus explicitly requested live subscription probes. No deployment or model substitution follows from test success.

Watchdog counters and disabled route state are process-local; journal records and queued wakes persist. Marker maintenance and hook-local log forwarding remain separate audit follow-ups. A dead or globally blocked kernel still requires an external supervisor. Driver I/O errors and state-save failures are monitored; memory sweep runs on a separate thread so a stalled sweep does not block alarm polling.

Periodic jobs retain a deadline between runs. Quota refresh runs every 10 minutes after completion, memory decay every hour after completion, and maintenance every 500 ms after completion. Each registers before its thread starts: a missing first start alarms after 120 seconds. Completion arms the next expected start at its cadence plus 120 seconds of grace; a start switches to the existing execution budget (quota 60 seconds, memory/maintenance 120 seconds). Missing starts and completions share the same persisted PID1 alarm path and remain deduplicated until successful completion. The socket loop polls independently so loss of the maintenance thread cannot disable its own alarm. Memory's dedicated loop replaces the maintenance tick counter; waits use monotonic deadlines to avoid accumulated tick drift. Healthy maintenance ticks are not journaled.

Codex BriefFold requests use exec’s supported `--output-schema` with the brief fields and notes, including open-item IDs. Readiness remains `UNVRS_SUMMARY_READY`; recovery remains ordinary progress text, so neither uses the BriefFold schema. Summary parsing takes the final agent message while checking every item for forbidden tools or errors. MemoryIndex still validates open-item retention independently. Successful startup and request route receipts, failed route reasons, and overall startup completion appear in the existing snapshot recent feed.
